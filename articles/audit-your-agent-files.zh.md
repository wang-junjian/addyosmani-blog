# 审查你的智能体文件

> 原文：[Audit your Agent files](https://addyosmani.com/blog/audit-your-agent-files/)
>
> 发布日期：2026-08-27

---

**TL;DR：你给编码智能体做的配置是有半衰期的。模型在进步，harness 在增加能力，代码库在变化，而我们为更早版本写下的那些指令却留在原地。近期研究发现在个性化技能上得到的效果并不一致。我现在每隔几周跑一次 Claude 的 /doctor，单独审查一遍记忆，并让每一条指令重新证明自己配得上留下的位置。**

我总觉得关于技能文件、以及该怎么处理你的 CLAUDE.md 和 AGENTS.md，存在很多混乱——尤其是我最近几个月在 Twitter 上读开发者讨论的时候。人们一直在说：嘿，把技能和 CLAUDE.md/AGENTS.md 保持最新是个大痛点。很多时候，人们想让这些文件去引导自己的智能体，却很难把它们控制在 200 行以内，哪怕这是官方给出的目标。人们发现很难让它们保持精简。它们在推高 token 成本。你往里面加了又加，反而可能让智能体表现更差。

而我读到的官方指导是：你应该定期删掉自己的 CLAUDE.md、技能和 hooks，比如每两个月一次，只重建真正重要的部分。但我自己的经验是，人们会害怕——嘿，我不知道这样做会不会反而让情况明显变糟。我担心一旦这么做，质量会大幅下滑。而我并没有一个简单的方法能快速恢复或试着做这件事。我能用的模型配置组合太多了。所以这条建议听起来像是很容易试，但实际上并不总是如此。有时候这些 markdown 文件和实践会过时，害处大于好处。不过我确实认为，这条建议里有对的地方——模型和 harness 确实在变得好得多。

![深色幻灯片，标题为「你的智能体环境」，副标题为「一切在你和模型之间悄悄累积起来的东西」。八张卡片分两行排列。第一行：「上下文文件：CLAUDE.md、AGENTS.md——一点点超出 200 行的指导，一次加一条规则」；「能力：智能体技能——装一次，永久保留。有人从 250 个降到 25 个」；「能力：插件——这些打包会悄悄带上自己的技能」；「连接：MCP 服务器——还连着，很少被调用，却一直在产生成本」。第二行：「自动化：Hooks——每个会话都要付出延迟，永远如此」；「状态：记忆——你整理干净的仓库里，过期的偏好依然活着。用 /memory 审查」；「捷径：命令、子智能体——常常只是在重复上下文文件已经说过的话」；以及一张高亮的黄色卡片「约束：权限、设置——这里唯一真正能约束智能体的规则」。下方横幅写着「这些每一样当初都有被加进来的理由。审查只是问一句：那个理由今天还成立吗？」页脚注：「安装一个有用的技能，和永远保留它，是两个不同的决定。」](../images/audit-your-agent-files-01.webp)

## 我很喜欢技能。但那些批评依然成立。

我个人是智能体技能的忠实拥趸。我和几位朋友维护了一些智能体技能包，还算有点热度。我维护 [Agent Skills](https://github.com/addyosmani/agent-skills)，这是一个聚焦 SDLC 的技能包。我的朋友 Paul Bakaus 维护 [Impeccable](https://impeccable.style/)，这是一个聚焦设计的技能包。而用技能配合编码智能体的开发者，整体反馈相当正面。技能被视为把通才变成专才的一个不错的抽象，对吧？而且它们和很多不同的编码智能体、harness 都能配合得不错。所以大家喜欢它们。

其中一类批评是站得住的。当然，写技能的人来自差异极大的领域。目前并没有一份很好的操作手册告诉你该怎么做。所以我们其实都在摸着石头过河。我们试着互相学习，吸收社区的反馈，不断迭代这些东西。但技能的卫生依然非常重要。有时你会看到一些技能包描述很单薄，或者对它们对应的工作流说得比较含糊。所以我仍然相信智能体技能，也认为它们很有价值。但随着大家在过去几个月里真正开始倚重它们，审查技能也变得越来越重要。

你可能在任意一天并行做一堆不同的项目或任务。对其中一些，你可能会试用新的社区技能，或者试着为它们拼出你自己的技能。可以想象，几个月下来，这些技能会在本地越攒越多，而你大概不会全都用得上。你实际用到的可能只是其中一小部分。

我去读 Hacker News 上关于公开技能的讨论帖时，争论大体是这样的：有人从技能中获得了价值；有人称它们是净负面；有人觉得关于价值的证据不够充分；还有人觉得它们只是增加了很多噪音、token 成本很高、而且不可靠。我当然认为这里面有很多合理的反馈。要针对每个人的工作流都拿出足够证据，证明这些东西确实是净收益，有时确实很难。但也有很多人说自己从中受益，同时也有很多反馈是成立的——比如：向我证明它真的足够有用，值得我在自己的项目里考虑。

## 为什么智能体配置会腐烂

每次看到智能体把自己带偏，人们就会往 CLAUDE.md 和技能里加规则。我这些年来也肯定这么干过。然后文件膨胀，遵循度下降，你加越来越多的规则，质量反而可能变得更差。你几乎把它当成了一个完整的知识库，而不是一份简短的决策指南。这是一个非常经典的错误。

![深色幻灯片，标题为「为什么智能体配置会腐烂」，副标题为「没有人一开始就打算写一份上千行的指令文件。它是这样一点点棘轮式地长出来的」。一个四步循环从左到右展开：「智能体出错了（就一次，但痛得印象深刻）」→「你加了一条规则（单独看很合理）」→「文件变长（把重要的东西稀释了）」→「遵循度下降（质量随之变差）」，并有一条虚线回路标注「然后循环再来一遍」。一个标题为「在我自己的文件里，这会长成这些样子」的面板列出：示例比它所说明的规则长得多；README、manifest 或技能文件里已经承载过的内容；智能体每出一次错就再加一条规则，而且从不删除；规则具体到仍然错过你真正想要的结果。结尾一句：「你想要一份简短的决策指南。你造出了一个知识库。」并附注：大多数被审查的文件都超出了 Anthropic 给出的 200 行指导，有些达到数千行，而且每个会话都要为它们付费。](../images/audit-your-agent-files-02.webp)

AGENTS.md 和 CLAUDE.md 的膨胀是另一个大问题。我觉得这一点现在已经被相当广泛地承认了。有人对真实仓库做过若干不同的研究，发现了很多相当常见的配置异味。上下文膨胀很常见，技能泄漏、lint 泄漏也是。而这些研究试过的大多数智能体文件，至少存在一个问题。文件普遍会超出 Anthropic 给出的 200 行指导。有些甚至达到数百或数千行，在每次会话中浪费 token。

这件事我也有责任。回头看我自己过去拼出来的那些 CLAUDE.md——不是用来分享，只是我自己环境里的——我也超过了 200 行。我发现自己的文件里有几种常见的失败模式。比如过长的示例；README、package manifest 或技能文件里可能已经存在的冗余内容；智能体每出一次错就加一条规则。这种增长会不断复利。所以我觉得你必须非常、非常聚焦地思考这件事。我还发现，在 CLAUDE.md、AGENTS.md 里写得过度具体，有时并不能真正带来你想要的结果。

说数字：[一项 6 月的研究](https://arxiv.org/abs/2606.15828) 考察了 100 个热门仓库，发现在 62% 的仓库里存在 lint 相关泄漏，42% 存在上下文膨胀，35% 存在技能泄漏。而在[《上下文工程的新规则》](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models)一文中，Anthropic 表示他们为 Claude 5 代模型删掉了 Claude Code 系统提示词的 80% 以上，而在内部编码评测上没有可测量的损失。这个结果不是一个目标；评测并未公开，而且它覆盖的是特定 harness 中的特定模型。教训是：指令的价值是会过期的，所以先归档；如果某条规则必须永远成立，就把它编码进测试、hook 或权限里，而不是留成一段模型可能丢掉的散文。

我觉得过去几个月我读到了一些非常好的研究，一些不错的实证研究，也许能帮助这场讨论。我想确保自己能在一篇文章里讲清其中一部分，因为我想有些人也没时间读这些论文。

![深色幻灯片，标题为「研究究竟发现了什么」，副标题为「在你为任何东西辩护或删除之前，值得知道的六个结果」。六张卡片各配一个小标签和一条主要发现。「AGENTS.md 中的配置异味，100 个仓库」显示「62% lint 泄漏、42% 膨胀、35% 技能泄漏」，并说明大多数被审查的文件至少带有一种异味，而且这些异味经常同时出现。「上下文文件对编码智能体有帮助吗？288 次运行，17 个任务」显示「正确性上没有明显提升」——它们改变了智能体的工作方式，而不是成功的频率；有一份指南提示测试套件很慢，于是跑针对性测试浪费的时间更少。「个性化技能有帮助吗？206 个会话，13 位开发者」显示「通用胜过个人」，合并构建的技能更可靠，并附一句说明：该研究使用的是 LLM 开发者模拟器。「智能体需要什么上下文才能行动？」显示「源码 27 / 45，摘要 4 / 45」，并指出约 9% 的字节完全相同重跑会改变结果。「handbook.md，20 到 124 页的政策手册」显示「严格通过率 36.2%」，为 30 种模型配置中的最佳，智能体有时先找到了相关规则、随后却违背它行动。「Anthropic，上下文工程的新规则」显示为 Claude 5 代模型「删掉了 80%+ 的系统提示词」，且内部编码评测上没有可测量的损失。页脚：指令的价值会过期；删除之前先归档，把硬约束放在比散文更硬的地方。](../images/audit-your-agent-files-03.webp)

## 个性化技能对编码智能体有帮助吗？

我一直在想，如果 Claude Code 或 Codex 能逐渐学会我喜欢怎么工作，会有多大用处。也许我偏好小改动，希望测试以某种方式运行，或者不希望智能体去重构无关代码。[这篇论文](https://arxiv.org/abs/2608.10319) 试图把这种交互历史变成一个可复用的个人技能。令人意外的结果是，个性化并没有帮上多大忙。基于某位开发者历史构建的技能，表现和从别人那儿借来的技能差不多。而基于许多开发者构建的通用技能，整体上更有用。

对我们很多人来说，我们会觉得为自己特定工作流准备一堆技能能带来巨大差别。但一些研究其实表明，情况未必如此——基于更广泛的工程实践、更广泛的社区最佳实践的技能，反而可能更合理、也更有价值。另外，抱歉，我还应该说明：它们能带来价值的地方，是当你的技能包含更多针对具体任务的示例时。有时那些更宽泛的社区技能就会有这些内容。比如，如果我要处理一个和调度相关的问题，而调度有很多不同的做法，也有不少怪癖。如果我手上的技能——不管哪些——带着一堆非常具体、非常明确的例子，也许这些就能以某种方式引导智能体。否则，只是写点「我希望我的调度原语的格式长这样」之类的细节，其实没那么有用。

当同一个偏好在多个相似任务上反复出现时，个性化看起来更有前途——不过这些实验用的是基于 LLM 的开发者模拟器，所以请把这当作「有希望」而不是「定论」。我的结论是：先从一个强力的通用技能开始，再逐步加入个人规则。我不会因为自己提过一次某个偏好，就把它提升为智能体的永久记忆。

再说回技能。当我和公司、和企业交流时，他们认为这价值很高。他们觉得单个工程师的技能有用，但当你有了一组面向团队或组织的技能时，他们认为那能带来复利式的价值，这挺酷的。你的工程文化被捕捉在里面，你的合规规则、你的品牌、你内部工具的怪癖、你希望如何在人和不同编码智能体之间保持一致、你希望如何做评审流程、资源配置等等这些东西。

## 上下文文件对编码智能体有帮助吗？

我一直把 AGENTS.md 和 CLAUDE.md 这类文件当作编码智能体的操作手册。[这篇论文](https://arxiv.org/abs/2607.27250) 问的是：这些文件是否真的帮助 Claude Code 和 Codex 解决更多任务。在 17 个真实任务上的 288 次运行中，它们并没有对正确性产生明显差别。

不过，上下文文件确实改变了智能体的工作方式。在某个仓库里，指南警告说完整测试套件非常慢。Claude 的回应是跑更有针对性的测试，浪费的时间更少。它在实现这个功能上并没有变得更强，但它更高效地遵循了该仓库的工作流。我认为这是那个有用的区分。上下文文件可以告诉智能体哪些命令昂贵、哪些文件是生成的、架构边界在哪里、或者项目特有的安全规则。它未必能教会智能体如何做一个微妙的设计决策；那些「差一点」往往归结为实现层面的判断力，而再多仓库散文也解决不了这些问题。

我的结论是：让仓库上下文文件聚焦在模型无法轻易从代码中推断出来的东西上——如何跑正确的检查、哪些操作昂贵、哪些东西不能碰、以及那些不寻常的项目约定在哪里。我不会用「写干净代码」这类通用建议把它们填满。[一项相关研究](https://arxiv.org/abs/2607.09691) 指向同一个方向：散文式摘要回答了 45 个关于代码的行为问题中的 4 个，而源码本身回答了 45 个中的 27 个，因为摘要会把那些真正重要的小细节抹平。让智能体去看真实的代码，而不是对代码的描述。

![深色幻灯片，标题为「上下文文件是干什么用的」，副标题为「在 288 次运行中，它没有让智能体更正确，而是让它们以不同方式工作」。两栏对比该保留什么、该砍掉什么。左栏以黄色高亮，标注为「值得写下来的：它无法推断的东西」，列出如何跑正确的检查、哪些操作昂贵、哪些东西不能碰、哪些文件是生成的、以及不寻常的约定在哪里，并有一个提示框说明某份指南提示测试套件很慢，于是 Claude 跑了针对性测试、浪费的时间更少。右栏「不值得花 token 的：散文教不会的东西」，列出微妙的设计判断、关于写干净代码的通用建议、对已存在代码的摘要、以及 README 里已经说过的任何内容，另有一个方框注释标题为「为什么摘要会失败」，说散文回答了 45 个行为问题中的 4 个而源码回答了 27 个，因为摘要恰好把重要的细节抹平了。结尾一句：「让智能体去看真实的代码，而不是对代码的描述。」](../images/audit-your-agent-files-04.webp)

## 我审查自己配置时发现了什么

看到 Claude 在 Claude Code 里推出 doctor 命令，我真的很高兴。这是一个很好的卫生命令，它基本上会做一次体检，检查相对于上下文成本而言未被使用的技能、MCP 服务器和插件，检查你的 CLAUDE.md 是否写得过度具体、hook 是否缓慢，或者有没有各种残留垃圾。而当我在自己的配置上跑 doctor 时，我被那些还挂在那儿、而我完全忘了的东西惊呆了。比如，如果你问我，我根本猜不到它们还在。我甚至忘了自己曾经试验过它们。

![深色幻灯片，标题为「两个都叫 doctor 的东西」，副标题为「一个审查你的配置，另一个检查你的安装。人们总是把它们混为一谈」。左侧面板以黄色描边，标注为「在交互式会话里」，描述「/doctor——配置审查」，它会指出相对于上下文成本看起来未被使用的技能、MCP 服务器和插件，给每个会话增加明显延迟的 hook，重复的 CLAUDE.md 指导，以及智能体本来就可以直接从仓库读到、却被始终加载的内容；一个提示框说明它只报告发现、不先做改动，并说明裁剪 CLAUDE.md 需要 Claude Code 2.1.206 或更高版本。右侧面板「在会话之外的 shell 里」，描述「claude doctor——安装诊断」，这是对你安装情况的只读状态检查，它不会去看任何一个技能、hook 或上下文文件，另有一个方框注释标题为「陷阱」，解释说这就是为什么有人反馈 doctor 只显示一个状态检查——他们用错了 doctor。结尾一句：「/doctor 是分诊，不是判断」，并指出它无法知道像「永远不要改动这个协议字段」这样的规则，是在保护一个正在运行的客户集成，还是在记录一个上季度就已经删掉的系统。](../images/audit-your-agent-files-05.webp)

我举一个例子。在某个时间点，大概四五个月前，我对大家在看的不同写作技能很好奇。当时有很多反废话（anti-slop）技能在被试验。于是我试了一堆不同的。然后我震惊了，因为我完全忘了自己装了多少个。我毫无概念。比如，这些东西会一起被触发吗？还是一个会压过另一个？它们是不是都被忽略了？我根本没意识到这些东西还挂在里面。所以审查一下非常有用。还有一些朋友写的设计技能，我当时在试，后来忘了。而现在，随着社区在某些情况下已经收敛到一些高质量技能上，我更愿意依赖那些，而不是几个月前试过的其他实验性技能。

我记得最近看到一条推文，有人说：对，我开始审查自己的技能，从 250 个降到了 25 个。我当时就想，你是怎么攒到 250 个技能的？太疯狂了。但大量试验社区技能，这些东西很容易随时间复利累积。而你不想把自己的智能体搞糊涂，对吧？所以你必须定期 lint 并清理你的智能体环境。

安装一个有用的技能，和永远保留它，是两个不同的决定。

## 审查质量，而不只是数量

关于技能，另一个要点就是确保它们是高质量的。Anthropic 自家的 Skill Creator 现在包含评测和一个基准模式，用来检查质量。社区里也有不错的工具来检查 SKILL.md 的质量。比如，描述写得好不好、触发条件写得好不好、步骤和示例是否清晰？也有一些更偏安全方向的审查工具和技能的实践规范。

有一个命名陷阱值得知道：在 Claude Code 里，会话中的 `/doctor` 是配置审查，而在 shell 里的 `claude doctor` 只打印安装诊断信息，这就是为什么有些人反馈 doctor「只显示一个状态检查」。另外，已安装的技能并不会把整个正文塞进每一个提示词：名称和描述会在[一个列表预算](https://code.claude.com/docs/en/skills)内加载以供发现，默认是上下文窗口的 1%，而正文只在被调用时加载。我还会用 `/memory` 单独审查记忆，因为即使项目文件已经整理干净，自动记忆仍可能保留过期偏好。

## 定期审查，然后测试移除

所以我认为，从个人角度这是很有价值的：大概每两周，甚至一个月一次，跑一次 doctor 检查你的技能和配置，审查自己在做什么，看看——好吧，哪些还成立？然后如果你有时间，真的去试试：比如把技能删掉，或者指示你的智能体：完全不要用任何本地技能。只试着用原始的模型和 harness 完成这个任务。看看不用这些技能是否真的没问题。然后你可以问自己：好吧，也许我可以把这些技能删掉。也许没关系。

![深色幻灯片，标题为「定期审查，然后测试移除」，副标题为「每两周一次。关键在于让撤销始终保持廉价」。五个编号步骤从左到右：01 归档，先把配置拍个快照，让恢复只需要一分钟，正是这一步让其余步骤变得安全；02 对技能、插件、MCP 服务器、缓慢的 hook 和重复的指导跑 /doctor，然后再跑 /memory，它会按自己的节奏腐烂；03 移除它标记出来的、以及你已经不记得装过的东西；04 不带它们测试，以黄色高亮，跑一个真实任务，并告诉智能体完全不要用任何本地技能，只用原始模型和 harness；05 决定，保留这次删除，或者用一条命令恢复。一个标题为「把第 04 步当作冒烟测试，而不是证明」的面板指出，即使温度很低，智能体的结果也会有波动，所以如果这个决定重要，就该重跑一次；而「恰好以某个技能本来要防止的方式失败」也是有用的证据——这说明那个技能又挣回了自己的位置。结尾几句：「我们保留东西，是因为移除它们感觉不安全」，这通常是在赌模型和 harness 自你写下那条规则以来没有进步；以及「让配置尽可能精简，同时按需保持具体」。](../images/audit-your-agent-files-07.webp)

但我觉得，有时我们把技能和所有装进来的这些东西当成拐杖，因为觉得删掉不安全，因为不信任模型和 harness 真的变好了。所以我认为，这里有很多可以试验和学习的地方。

持续保持卫生。审查质量、安全性。定期跑 doctor 命令，并尽量确保你的本地配置尽可能精简，同时按需保持具体。
