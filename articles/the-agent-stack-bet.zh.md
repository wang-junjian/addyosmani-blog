# 智能体技术栈的赌注

> 原文：[The Agent Stack Bet](https://addyosmani.com/blog/the-agent-stack-bet/)
>
> 发布日期：2026-04-18

---

掀开今天大多数「生产环境智能体」的引擎盖，你不会看到智能。你会看到定制的管道、脆弱的会话逻辑、共享的服务账号，以及一个靠希望勉强维系的安全模型。这本来可以好得多。

如果你过去 18 个月一直在把智能体推上生产，你已经知道模型和工具变好了多少——*好得惊人*。你也知道，那些仍在烧掉你 on-call 轮值的问题，不是靠写提示词就能绕过去的问题。我们正在撞上一个**技术栈天花板**，它正在悄悄制造一个**治理**与**可靠性**的缺口，而下一代智能体系统无法靠长大来穿过它。

现在整个行业都在忍受一种我可以称为*过度代理*的状态：**给自主系统宽泛的权限去把事情做成**，然后就放任它们在生产环境的运行时里去发现——某个 schema 漂移了、某个 API 变了、或者某个下游服务开始返回它本不该返回的个人身份信息。智能体把任务标记为「完成」，身后留下一串被破坏的状态。人类在周一才发现。

这不是构建智能体的人的失败。这是他们所依赖的技术栈的失败。

我认为每个认真的团队在未来十二个月里都必须做出下面这四个架构上的押注。

## 1）智能体需要身份，而不是共享凭据

每一个把智能体推上生产的工程师都熟悉这种特定的恐惧：你有智能体在做有用的工作，而你对它们碰过哪些工具、搬过哪些数据、用了哪些凭据去做，实际上零可见性。我管这叫*治理债*——安全与审计风险的无声累积，最终会逼着一次彻底重写，而那通常发生在第一个捅到 CISO 的事故之后。

根因在于今天大多数智能体都是幽灵。它们没有身份。它们借用一个服务账号，继承某个人的 OAuth token，然后「承诺」——在应用代码里、在提示词里——待在线内。在真实的企业环境里，提示词里的承诺不是策略。

**我的押注是：智能体身份必须从应用层下沉到平台层。**

差别在于「外挂的安全」和「内嵌的安全」。外挂的样子是每个工具调用前面加一层中间件，客客气气地请求智能体乖乖的：容易被绕过、延迟代价高、而且对你现有的 IAM 不可见。内嵌的样子是焊在钢架上的刷卡门禁。智能体有一个独特、无法伪造的身份，在网络和平台层面被识别，策略在源头被执行。如果智能体去够一个它没被授权的数据库，连接根本不会打开。没有中间件，没有玄学。

做对了，这会把「一支负债舰队」变成更像一支受管理的劳动力的东西：每个动作可归因，每项权限可审计，每个智能体一个调用就能撤销。

## 2）智能体需要普适上下文，而不是爬来的窗口

上下文管理是眼下每个构建者都在交的一笔税。团队把很大一块工程时间（还有 token）烧在无差别的管道上——自定义序列化、定制的会话存储、手搓的记忆层——只为了让一个智能体在多步任务中途别把自己的使命忘掉。

更糟的是，智能体*能*够到的上下文通常是孤岛式的。一个基于浏览器的智能体能看到打开的标签页。一个桌面壳能看到用户碰巧拖进来的文件。它们都没法同时跨业务真正所在的那几个系统去推理——CRM、ERP、数据仓库、工单系统、会议记录、项目计划。

**智能体需要的是在平台层集成的普适上下文。** 如果我们不修好这一点，就该老实承认智能体化 AI 的天花板是「稍微好一点的电子表格自动补全」，而且我们应该停止再写关于它的愿景文章。

# 3）智能体需要能在你合上笔记本之后继续活着

这里有个不太好听的版本：今天作为「一个智能体」交付的很多东西，还没准备好在一个企业里铺开部署。

我想说得精确一些，因为前沿在过去六个月确实往前走了。Claude Code、OpenClaw 以及类似平台这样的环境已经够用了——持久化的任务状态、定时执行、多智能体协同，以及能在断连后存活的长时间运行会话，这些都不再是空想。它们不是玩具。问题已经往前移了。

现在的问题是，一个智能体能不能跑一周，而不是一小时。它能不能穿过三次交接、两次凭据轮换和一个审批闸门，而不需要一个人守着会话。它周二做的工作，周五能不能被一个不在场的人审计。一个能扛住 WebSocket 掉线的会话只是入场券。一个能跨越一个季度的使命，才是企业真正需要的门槛。

真实的工作装不进一个会话里，而且大部分也装不进一天里。一个采购流程横跨数周、十几次交接。一次合规审计要跑一个月。一次事故调查活得比三轮 on-call 轮值还长。

**今天大多数智能体会撞上一个硬天花板——有时是基于时间，有时是基于 token，有时是基于治理——撞上的时候，使命就失败了，然后由一个人从对话记录断掉的地方收拾残局。**

企业级的自主性要求持久的、云原生的执行，而且地板要比「会话没掉」高得多。具体来说，这意味着：

- **状态**和**检查点**默认就能扛住重启、断连、重新部署和模型版本变更——而不是靠一个本地 Redis 加一段祷告硬挂上去。
- **活得比窗口更长的上下文**：长周期记忆、摘要，以及智能体实例之间的交接，这样一个跨周的任务不会因为某一次运行把 token 用光就死掉。
- **活得比会话更长的使命**：智能体跨天、跨交接、跨凭据轮换地待在活儿上，并且有一份你睡觉期间发生了什么的审计轨迹。
- **一等公民的人在环原语**，这样智能体可以停下来请求许可去做一件新事，而不是默默判定自己有权这么做。

带护栏的持久化。这就是门槛。低于这个，你造的就是碰巧能跑很久的 demo。

# 4）智能体需要平台

我在强队里最常看到的模式也是最让人难过的一种：出色的工程师把带宽耗在那些不能让产品差异化的技术栈问题上。自定义记忆。定制评测 harness。自建的观测能力。手写的重试逻辑。一个勉强能用的追踪系统。这些都不是智能体时代的难点，也没有一样是你的用户在付钱买的东西。

真正的价值在领域推理和业务逻辑里——那些针对你的公司、你的客户、你的监管环境的判断。底下的一切都应该是你*所依托*的平台，而不是你*亲手搭*的管道。

这就是为什么开放原语的成熟现在很重要。开源编排框架存在的意义，正是让脚手架不被锁在任何单一厂商的路线图后面。那套在云计算、容器和 CI/CD 上奏效的模式——在开放原语上本地起步，准备扩展时升级到托管平台——正是智能体平台需要照抄的模式。

**团队应该能在自己的笔记本上，用他们将来在生产环境里运行的同一套积木做原型，并且不经过重写就能跨过这道边界。**

那才是让团队停止和管道打架、回到产品上的工程标准。

## 五年视野

未来五年跑在前面的团队，不会靠更会写样板代码而跑在前面。他们会靠**选对智能体基座**、把工程时间花在***只有他们能解决***的问题上而跑在前面。

每一个月花在重建通用技术栈上——身份、上下文、持久化、编排——就是一个月没花在真正让你的智能体值得部署的逻辑上。

**智能体技术栈必须变成一个已被解决的问题。** 唯一真正的问题是：你想自己再解一遍，还是想建在一个从底层开始就是为智能体设计的基座之上。

我押后者。我认为你也该押后者。
