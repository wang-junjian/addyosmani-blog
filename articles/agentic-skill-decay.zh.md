# 智能体技能退化

> 原文：[Agentic Skill Decay](https://addyosmani.com/blog/agentic-skill-decay/)
>
> 发布日期：2026-08-31

---

**精通仍然来自一遍遍的练习。**

在智能体出现之前，我的练习是写代码的一部分：尝试不同的做法，调试出错的地方，评审别人的代码，大量阅读。智能体可以跳过其中大部分工作，所以**积累这些练习必须刻意为之**。

如果我刚入行，我会在写提示词之前先形成一个假设。多问「为什么」，读 diff，试着预判什么可能失败。偶尔也手动把问题自己走一遍。

![幻灯片标题为「精通仍然来自练习：过去练习会自己找上门，现在你得主动去争取」。上排展示过去练习如何作为写代码的副产品自然出现：尝试一种做法、看它失败、追踪 bug、读别人的修复、把教训带走。下排展示智能体面对同一个问题的过程，从问题直接到可用的补丁只需几分钟，而「看它失败」「追踪 bug」「读别人的修复」三步被置灰。所以要把练习有意地放回去：在写提示词前先形成假设，多问为什么并持续追问，读 diff，预判什么可能还会失败，偶尔手动走一遍。页脚：我仍然激进地使用智能体，我只是不希望问题已经关闭，而我的心智模型还停在原地。](../images/agentic-skill-decay-01.webp)

以我的经验，**出色的智能体工作依赖两种能力**：

1.  **深厚的专业能力：** 你对问题域的理解足够深，能够定义什么才算好结果。理解你的用户、产品、业务也是其中一部分。
2.  **应用判断力：** 用你的品味把它变成一个清晰、可测试的计划，方式是选对上下文、约束、测试和验证手段。

为了建立这些，我会练习的技能是决策、写规格、纠偏和验证。

![幻灯片标题为「出色的智能体工作依托两种能力：智能体写补丁，而这两种能力决定这个补丁值不值得写」。第一种是深厚的专业能力，也就是应该发生什么：你对领域理解足够深，能定义好的结果，包括用户是谁、他们需要什么，系统实际如何运作，以及哪个边界情况会让这个功能变得毫无用处。第二种是应用判断力，也就是什么能让我相信它确实发生了：把品味变成一个清晰、可测试的计划，包括该交给它什么上下文、它不可越过的约束，以及让「好」具体到足以被检查的测试和验证。所以值得练习的四项技能是：决策，选择什么值得做；写规格，让结果明确；纠偏，在过程中纠正它；验证，判断证据是否足够。](../images/agentic-skill-decay-02.webp)

## 我真正做过的那些练习

我刚进入软件工程这一行时，非常强烈地觉得自己完全不知道在干什么。我构建东西构建得很开心，尝试各种做法很开心，失败、从错误里学习，然后每一次都在路上往前走一点、再走远一点。每次失败，我都尽量把它当作成为更好工程师的又一块积木。所以这些工作全都是我在做练习。我就是这样学会 JavaScript 的。我就是这样学会用 C++ 编程、构建桌面应用的。我就是这样学会调优图形密集型应用性能的，诸如此类。

在积累练习的过程中，我常常会带着某种假设或想法进入一个任务，哪怕那个假设关于事情如何运作的判断错得很离谱。我会先试我认为可能行得通的做法，等它不行了，我就去 Stack Overflow 或上网搜各种文档，吸收一些知识。如果话题非常冷门，也许还会读点书。然后我继续往前走。这样做足够多次，你就开始积累出专业能力，尤其是当你开始真刀真枪地干、在真实世界的项目上试，而不只是周末玩票的时候。

我今天用到的绝大部分判断力，都来自成千上万次这样的小练习：调试失败、评审别人的代码、与那些看起来很美直到真实系统推回来才露馅的抽象共处。智能体现在可以跳过其中大部分工作。**如果你职业生涯才走到第三年，看似合理的代码到来的速度，可能已经快过你判断它的能力。**

## 短路

我认为，对很多刚开始用 AI 的人来说，你可以在很大程度上把那整段学习旅程短路掉。你可以非常快地从事「嘿，这里有个问题」跳到「嘿，这里是解决方案」，或者「这里是整个任务的结果」，同时跳过那些本来会构建你的知识库、本来会教育你「别那么干」「这就是为什么你不能那么干」「应该这么干」、并帮你推理权衡取舍的所有环节。我认为这正是一个尤其需要初级工程师主动规划自己学习路径的领域。

我也和一些 AI 实验室聊过。当下 AI 领域许多主要玩家都非常专注于帮你尽快达成一个结果或者拿到一个答案，除非你明确把「教育我」列为目标之一，他们并不一定会在这条路上帮你。比如，「帮我做一个排班应用」和「帮我做一个排班应用，并在做的过程中一步一步教我怎么做的」，这两句话是不一样的。大多数人不会说第二种。一部分原因是不知道还有这个选项。一部分原因可能是想着，哎，现在有这么多关于速度的期待，有这么大的压力要快速交付、赶紧进入下一件事。但我确实认为，想成为更好的工程师、想继续拥有这种能提升我们品味和判断力的专业能力，你就得特意绕路去积累精通。

## 完成一个任务不等于一次练习

我认为面对任何一种批判性思考、任何一类问题，对解决方案先有个假设、对它将长什么样先有个想法都是有用的：如果只谈逻辑和代码，那是它的形状；如果是一块 UI，那是它可能长什么样、感觉如何、怎么交互。**一个任务完成了，并不必然意味着你学到了什么。** 它只意味着这个任务完成了。你几乎得主动去找那些学习机会，或者你可以让智能体在构建过程中、或者在最后总结：对像我这样的中级开发者，或者对初级开发者来说，这里面有哪些关键的经验能帮我扩充知识库、改善我思考问题的方式？你可以一直这么做。你只是必须对自己的学习路径主动一点。

对我来说，这些天有几件事我能用 AI 来做，更复杂的三维图形编程肯定是其中之一。我不是这方面的专家。确实有些时候我会特意确保自己在问 AI：好，那你能解释一下这东西是怎么运作的吗？你能教教我你刚刚实现的这个概念吗？你能帮我理清这些不同的元素是怎么连起来的吗？我觉得正是因为我想学、我有那种学习的欲望，我才会和我的智能体配对来做这件事。如果你并不想学，你就在那里丢掉了机会。

「完成的任务不等于一次练习」这件事，在过程中没有出错的时候也会发生。当出现错误时，你会开始想，好，那它为什么出错了？哪里可以更好？我有什么没想到的？这迫使你反思。当事情顺利时，其实并没有教学时刻。你只会想，好，活干完了，我接着做下一个任务吧。所以，尤其如果你是初级工程师，你会想要主动去找那些能不断升级自己的机会。

Anthropic 有一项 [2026 年的研究](https://www.anthropic.com/research/AI-assistance-coding-skills)，观察初级工程师学习一个特定的 Python 库 Trio。**使用 AI 助手的人在后续测验中得分 50%，而手动动手的那组是 67%。** 而在 AI 组内部，成绩好的那些人靠的是提概念性的问题、要求解释，而不是把模型当成代码自动贩卖机。这和我前面说的是同一件事：如果你只是用 AI 生成输出、生成结果，而不是把它当搭档、不用它来尝试提升你的批判性思维、你的知识、你对事物如何运作的理解，你最终可能落到这种境地——你大体上并不理解事情是怎么运作的，你只是很会写提示词。而这意味着你在验证这一侧大概不会太强。提了问题、要求解释的人表现更好，这一点我并不太意外。那些人很可能对事情如何运作、如何与他们已知的其他东西相连做了多得多的反思。他们做模式匹配，他们开始积累残渣：好，这东西是这样运作的，我是这样推理它的，这些是我知识里的缺口。所以看到那 17% 的差距，我觉得说得通。当然，这只是一项关于单个 Python 库的短期研究，所以我不会说它一定是定论性的，但它仍然非常有意思。

我在学不熟悉的东西时仍然是这么工作的。我尽量让自己留在循环里。我在写提示词前先形成假设。我问为什么，检查 diff，预判什么可能失败，并给智能体一个具体的验证方式来核查它的工作。偶尔我会手动做掉一个小问题。我希望智能体关闭任务的同时，我的心智模型还在往前走。

![幻灯片标题为「四个值得放慢的地方：智能体从问题到补丁的速度快到让学习很容易被漏掉」。沿着一条从问题到补丁的时间线，智能体是直接横穿过去的，线上有四个介入点。在你写提示词之前，先写下你认为问题出在哪，先形成假设，再让智能体去验证它，看你猜得对不对。在它工作期间，多问为什么，不只是问它改了什么，而是为什么用这个做法、排除了什么、对系统做了什么假设。当补丁落地时，读 diff 并问还可能哪里会失败，这是整个循环里价值最高的一分钟，也是最容易被跳过的一分钟。以及每隔一段时间，手动把它走一遍，尤其是在你还在学习的那部分技术栈里，这很慢，但有些东西只能这样才进得去。重点不是少用智能体：在智能体之前，练习是写代码的副产品，现在它必须是有意为之。](../images/agentic-skill-decay-03.webp)

## 但还是激进地用起来

我不知道代码层面的专业能力还能像今天这样有价值多久。模型进步太快，很难有确定答案。我也不认为答案是回避智能体，或者把逐行手敲浪漫化。我在激进地使用它们。有些日子我同时跑五个、十个会话，有一次我还发现自己让错误的那个项目去加暗色模式。这个错误把约束讲清楚了：**智能体的吞吐量扩展得比我的注意力更快。**

## 在性能面板里泡上几千小时

我能想到一些我不得不花几千小时才做对的事情。性能优化就是这样一个领域：当年你并不总能找到大量优秀的博客文章或书籍可参考。有一些不错的、非常经典的文献会谈到内存，或者如何思考硬件和约束。但像 Web 性能优化、JavaScript 优化、堆优化这些事情，并不总有好的文章。所以你的练习是这么积累的：打开 Chrome 开发者工具，用性能面板对页面或应用跑一条 trace，与它交互，试着找出到底哪里慢。然后试着钻下去，形成一个假设：好，看起来火焰图里这一片是大部分问题所在。或者这里可能是内存面板里我没让垃圾被回收的地方，诸如此类。在我那个年代，你必须经历足够多的错误、反复尝试找根因的折磨，才能积累出这些知识——有时候相当冷门的知识——关于什么行得通、什么行不通。

如今，类似的流程会变成：让 DevTools MCP 配合你的智能体去做性能分析，把事情弄清楚，然后它自己给你提出修复方案。于是你就不再会那么深地积累起性能方面的专业能力了。

## 你只能提示出你能想象的东西

这些天刷 Twitter 时，我总是惊叹于我的信息流里有多少想象力和创造力。那么多设计师、创作者在分享他们正在构建的惊人着色器、惊人游戏、UI、沉浸式体验，而这些东西现在更加唾手可得。技术其实早就在那儿了，现在天花板变成了想象力。你要更快地构建这些东西，比过去容易得多、也容易太多了。但你必须先有那份想象力，才能先有那个想法，才能让智能体去实现它。然后你还得有那份专业能力去验证它。**所以验证是地板，想象力是天花板。**

![幻灯片标题为「验证是地板，想象力是天花板：技术早就在那儿了，现在真正限制你的是这两样」。天花板是想象力，因为你只能提示出你能想象的东西，而想法必须先存在，智能体才可能把它构建出来，所以抬高天花板就能问出更多可能。地板是验证，因为你只能保留你能确认是好的东西，这意味着要能注意到它是错的、并且知道为什么错，所以抬高地平就能更安全地保留。你真正能交付的一切都落在这两者之间。中间的示例是那个 3D 专辑网站的第一版：它渲染出来了，但它也用错了交互范式，在移动端表现很差，而注意到这一点需要专业能力，接着还需要一个关于为什么的假设。图注：只要你能想到，你就能做出来；而该不该保留它，是另一种技能。](../images/agentic-skill-decay-04.webp)

我记得，为了一个即将上线的专辑网站（我做音乐），我希望首页的一部分是这些可交互的 3D 物件，是体验的一部分。比如 3D CD 播放器，我记得里面还放了一台黑胶唱片机，可能还有一台磁带机，一些 90 年代的怀旧感。结果初版不仅看起来不够惊艳，而且没有遵循正确的交互范式。它们在移动端表现也不好。所以我首先得有专业能力去注意到它在某方面确实有 bug。也许任何用户都会注意到这一点。但接着我对为什么会这样得有个假设。然后我才能去自己 profile，或者让我的智能体去 profile，弄清发生了什么、哪里出了问题。也许只是交互逻辑的写法有些地方不太好。所以我认为你的想象力真的很重要，但你的专业能力同样重要。这两样都重要。只要你能想到，你就能做出来。

## 下一代还需要这种专业能力吗？

有一个合理的问题：嘿，如果智能体能做这些任务，而且做得越来越好，人类还需要积累这种专业能力吗？下一代还需要在一些冷门领域积累专业能力吗？我认为至少在今天，它仍然有用的地方，是那些智能体做得并不完美、工作需要被检查的地方。比如你让某个东西去优化一个特定的循环、一段动画、一个调度例程，或者任何类似的东西，而它可能是以牺牲别的东西为代价做到的。如果你不知道该看什么，或者你不知道怎么读实现、理解到底做了什么，你最后可能交付了一个实际上并没有实现你想要的效果的东西。

**技能和 MCP 可以编码一套有用的工作流。它们无法告诉你，这套工作流的假设什么时候已经不再适合你的系统。**

Anthropic 有一项[约 40 万个 Claude Code 会话的研究](https://www.anthropic.com/research/claude-code-expertise)，把专业能力看作一种任务特定的东西。研究发现，哪怕你对你试图完成的任务只有中级水平的专业能力，相比更新手一些的人，你达成经核实成功的几率也会更高。这并不意味着你必须在整个技术栈上有十年经验，但它确实意味着**你需要足够理解问题域，才能识别出「好」是什么意思**。如今我们有时把这件事称为品味，我之前也写过。这也是为什么，当我读 [Claude Code 最佳实践指南](https://code.claude.com/docs/en/best-practices)时，很高兴看到它开头就谈验证：测试、用截图、以及其他信号，给你的智能体一些它可以持续迭代的东西，也给你可以审阅的证据，而不是只给一句「任务已完成」的简单总结。拥有专业能力能帮你把黏土塑得更好，而没有多少专业能力的人也许能塑出个看起来还行的东西。

这一切都回到：得有那份专业能力，才能验证工作，才能评判智能体的工作。所以我希望，即便软件工程所用的抽象层级不断升高，我们仍然能继续投资于精通、投资于手艺。

## 专业能力的回报正在上升

我觉得软件工程的基础仍然会继续重要。专业能力仍然会继续重要。而且现在地板被抬高了，AI 也在提高人们所拥有的技能、所拥有的专业能力的回报。初级工程师是通过交付真实的东西、犯错、学习、积累练习，才不再是初级的。专家对什么该建、怎么验证、怎么确保你知道它是好的、它没坏、它可维护、它能扩展、它能在不同的上下文或平台上工作，有一种直觉。尤其是现在这么多人只要写提示词就能把一个想法变成现实，把它做到高质量、好到可以交付、令人愉悦，并且可维护、不会在生产环境里崩掉，这些技能会继续重要。

我每周至少会遇到这种事两三次。现在提示出任何应用、任何功能都太容易了。比如，我正在做一个文本编辑器，不是从零开始。它的想法大概是做一个写作辅助工具，标出你的语法可以更好的地方，或者标出你正在使用 AI 腔写作的那种情况。一个前沿模型在大量来回之后，能给我生成一个漂亮、看起来还行的 UI。但它并不惊艳。而且它有一堆问题，比如没有最优地利用屏幕空间。颜色对比度不好。滚动模型不好。所有这些我知道，都是因为我自己以前犯过这些错，我积累起了专业能力。但如果你没有那份专业能力，你可能只是提示出个东西，扔到世界上，然后就停了。而你并不知道什么更好，因为你没有花时间去积累那份专业能力。

## 把教训放在下一个智能体找得到的地方

我指导别人时经常讲的一件事是：当你和智能体一起工作时，你应该让它变得更好，它也应该让你变得更好。这意味着每天都应该有某种循环，把东西加进经验教训里、加进记忆里，或者加到某个地方，让它能够改进。因为否则的话，**每次你开一个新会话，感觉就像在给一个患有失忆症的新员工做入职**。他们不一定会记得你的业务、你的产品、你的团队、你的用户，或者任何这类细节。这就是为什么我们最终不仅要往技能里，还要往上下文、往我们试图交给智能体的所有东西里塞这么多内容。而且我们需要小心区分哪些是真正有用的、真正针对具体问题的，哪些只是我们以为会让事情变好的。所以我总是鼓励大家去看：你怎么确保自己在教智能体更多东西，怎么确保它每天都在变好、你也在变好？

如果你在聊天窗口里，恰好正在解决一个问题，比如说你发现你正在做的某个 UI 组件里有个很微妙的滚动 bug。你和智能体来回折腾，这里面某处有一条你将来可能用得上的教训。那么，这条教训也许会被加进记忆。也许不会。尤其是当它是一个发生了压缩的长会话，那条完整的教训不一定能进去。所以当聊天窗口一关，那条教训就可能消失了。而如果你改为把东西固化下来——具体的教训、测试、lint 规则，任何东西，尤其是小到可以在你的仓库里固化的东西——它就能教未来的智能体。我个人觉得这非常有帮助。如果我学到一条教训，我会花几分钟回顾一下，看它值不值得加进我的 lessons.md，或者让我的智能体把它加进记忆，或者做成某个能让它黏住的东西。因为我不希望教训消失。我个人会忘，我会转向下一个问题。这种情况对我来说一直发生。它可以是任何事，从「我对 UI 的处理方式有特定偏好」，到我怎么写组件、我怎么处理性能，各种都有。如果我处理某个问题有某种微妙的方式，我希望我的智能体能记住，或者有办法记住，而不是我每次都得重新说一遍。

我们常常把智能体当成会记住我们做过的一切的东西，而事实不一定如此。即便智能体有记忆系统，你也不能完全指望它回忆起你可能想学的所有有意思的东西，或者你喜欢的工作方式，或者你会怎么验证。所以开始把更多这类东西记录在 markdown 文件里是可以的。只是要非常小心、非常谨慎，不要在这上面过度投入、把它当成策略。我一直喜欢「双循环」这个想法。**一次好的、能让你学到东西的练习，应该磨利你，也应该磨利你的智能体。** 而当你有一个假设被纠正了，你可以考虑这个纠正是否值得变成一条 lint 规则、某个类型约束、一个文档约定或者一个测试，这样它就能留下来，在未来让你受益。

## 外层循环

所以我认为这一切在精通这件事上意味着：投资你的专业能力，投资你的手艺。去做练习，去犯错，从中学习。随着时间推移，你就能分辨出什么东西值得存在。你就能开始写计划、打磨计划、为「完成」给出某种定义，并且为那些人类仍要留在循环里检查正确性、安全性或用户影响的地方做规划。我认为这基本上就是今天的工程师需要自己负责的外层循环。我们会继续看到 AI 把工程推向更高的抽象层。而**我能运行的智能体越多，我就越需要谨慎地选择把有限的时间、品味和判断力放在哪里。**
