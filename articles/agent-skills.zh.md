# 智能体技能

> 原文：[Agent Skills](https://addyosmani.com/blog/agent-skills/)
>
> 发布日期：2026-05-03

---

*资深工程师的工作，大部分是那些不会出现在 diff 里的部分。规格。测试。评审。范围纪律。拒绝交付无法验证的东西。AI 编程智能体默认会跳过这些部分。Agent Skills 是我让它们不再可选的一次尝试。*

---

任何 AI 编程智能体的默认行为，都是走通往「完成」的最短路径。你要一个功能，它就写这个功能。它不会问你有没有规格，不会在实现之前写测试，不会考虑这个改动是否跨越了信任边界，也不会检查这个 PR 在评审者眼里会是什么样。它产出代码，宣布胜利，然后继续前进。

这是每一位资深工程师花了整个职业生涯学会避免的同一种失败模式。任何任务的资深版本，都包含不会出现在 diff 里的工作：暴露假设、写规格、把工作拆成可评审的小块、选择无聊的设计、留下结果正确的证据、把改动的规模控制到人真的能评审。这些步骤，正是能在规模化下交付可靠软件的工程师，和推代码然后弄坏东西的人之间的主要区别。

智能体跳过这些步骤的原因，和任何初级工程师会跳过的原因一样。它们是不可见的。奖励信号指向「任务完成」，而不是「任务完成且设计文档存在」。所以我们得把资深工程师的脚手架重新装回去。

[Agent Skills](https://github.com/addyosmani/agent-skills) 就是我对这套脚手架的尝试。它刚刚突破 27K 星，看来想要它的人不止我一个。**这篇文章讲的是 README 没有完全覆盖的那部分**：每个设计选择为什么存在，它如何对应到标准 SDLC 和 Google 公开发布的工程实践，以及即使你一个技能都不安装，也该从这个项目里偷走什么。

## 「技能」到底是什么

「技能」这个词在 Claude Code / Anthropic 的词汇里承担了太多含义，精确一点有帮助。技能是一个带 frontmatter 的 markdown 文件，在情况需要时被注入智能体的上下文。它介于系统提示词片段和操作手册之间。

技能*不是*参考文档。它不是「关于测试你该知道的一切」。它是一个工作流：智能体遵循的一系列步骤，带会产生证据的检查点，以一个明确的退出标准收尾。

这个区别就是全部关键。如果你把一篇 2000 字的测试最佳实践文章塞进智能体上下文，智能体读它、生成看起来合理的文本，然后跳过真正的测试。如果你放进去的是一个*工作流*（先写失败的测试、运行它、看着它失败、写最小代码让它通过、看着它通过、重构），智能体有事可做，而你有东西可验证。

**流程胜过散文。工作流胜过参考资料。带退出标准的步骤胜过没有退出标准的文章。** 这一个区别，就把一个有用的技能和一个漂亮的 markdown 文件分开。它也解释了为什么那么多「AI 规则」仓库在实践中什么也没做成。那些规则是文章。

## 技能编码的 SDLC

仓库里的二十个技能围绕六个生命周期阶段组织，上面再放七个斜杠命令。定义（`/spec`）是你决定到底在构建什么的地方。计划（`/plan`）把工作拆开。构建（`/build`）用垂直切片实现它。验证（`/test`）证明它能工作。评审（`/review`）抓出漏过去的东西。交付（`/ship`）把它安全地送到用户手上。`/code-simplify` 横跨整件事的底部。

这不是巧合。它和每一个正常运转的工程组织所跑的 SDLC 是同一个，只是词汇不同。Google 叫它设计文档 → 评审 → 实现 → 可读性评审 → 发布清单。Amazon 叫它逆向工作备忘录和抬杆人。每一个健康的团队都有这个循环的某个版本。

AI 编程智能体带来的新情况是，*大多数智能体默认会跳过其中大多数阶段*。你要一个功能，你得到一份实现，而规格、计划、测试、评审、发布清单全都不发生。**技能推动智能体走完一位资深工程师会强迫自己走完的那些阶段，因为没有这些就交付代码，正是你制造事故的方式。**

一个复杂功能可能会依次激活十一个技能。一个小 bug 修复可能用三个。路由器（`using-agent-skills`）决定哪些适用。重点是工作流随真实范围缩放，而不是随假设的范围缩放。

## 真正在承重的五条原则

项目里有五个设计决策是承重的。系统的其余部分都由它们推出。

### 1. 流程胜过散文

已经讲过了。工作流是智能体可执行的；文章不是。对人类团队也一样。如果你的团队手册有 200 页，在时间压力下没人会读。如果它是一小组带检查点的工作流，人们真的会去跑。

### 2. 反合理化表

这是项目里最有辨识度的设计决策，也是我最希望其他团队偷走的那个。

每个技能里都有一张表，列出智能体（或一个疲惫的工程师）可能用来跳过工作流的常见借口，配上写好的反驳。几个接近原文的例子：

- *「这个任务太简单，不需要规格。」* → 验收标准仍然适用。五行可以。零行不行。
- *「我之后写测试。」* → 「之后」是承重的那个词。没有之后。先写失败的测试。
- *「测试通过了，发吧。」* → 通过的测试是证据，不是证明。你检查运行时了吗？你验证用户可见行为了吗？有人读过这份 diff 吗？

这之所以有效，是因为 LLM 极其擅长合理化。它们会产出一段听起来合理的文字，解释为什么*这个特定的*任务不需要规格，或者为什么*这个特定的*改动不评审就合并也没问题。**反合理化表是预先写好的反驳，针对的是智能体还没说出口的谎。**

这个模式对人类团队一样好用。大多数工程腐化，不是有人选择做坏工作。而是人们接受听起来合理的理由，去跳过他们不想做的部分。一个把自己反合理化写下来的团队，是一个反合理化更少的团队。

### 3. 验证不可协商

每个技能都以具体证据终结。测试通过。构建输出干净。运行时跟踪显示出预期行为。评审者签字。*「看起来对」* 永远不够。

这也是让 Anthropic 的 harness 能从失败中恢复、让 Cursor 的规划者/工作者/裁判拆分真的能抓到 bug、让任何[长时间运行的智能体](https://addyosmani.com/blog/long-running-agents/)可恢复的同一个原则。智能体是一个生成器。你需要一个独立的信号来表明工作完成了。技能把这个信号烤进了每一个工作流。

### 4. 渐进式披露

不要在会话开始时把二十个技能全都加载进上下文。按阶段激活它们。一个小型元技能（`using-agent-skills`）充当路由器，决定哪个技能适用于当前任务。

这是把 [harness 工程](https://addyosmani.com/blog/agent-harness-engineering/)的教训应用在技能的粒度上。每一个被加载进上下文的 token 都会在某个地方降低性能，所以你只加载相关的，剩下的留在磁盘上。**渐进式披露就是你如何把一个二十个技能的库塞进 5K token 的槽位而不污染这口井。**

### 5. 范围纪律

这个元技能编码了一条我如果可以就会钉在每个智能体上的不可协商项：*「只碰要求你碰的东西。」* 不要重构相邻系统。不要删掉你并不完全理解的代码。不要路过一个 TODO 就决定重写整个文件。

这听起来显而易见，直到你看到智能体认定修一个 bug 需要现代化三个不相关的文件。**范围纪律是决定一个智能体的 PR 是可合并还是必须拆掉重来的最大单一因素。** 它也是最干净地对应到 Google 代码评审规范的那条原则——在那些规范里，评审者会拦下一个做了不止一件事的 PR。

## Google 的 DNA

这些技能浸透了《Software Engineering at Google》和 Google 公开工程文化里的实践。这是有意的。让 Google 规模的软件得以运转的东西，大部分都有文档且公开，而它*恰好*是智能体最可能跳过的部分。

哪条技能编码了哪项实践的部分映射：

- **`api-and-interface-design` 里的海勒姆定律。** 你的 API 的每一个可观察行为最终都会被某人依赖，所以要带着这一点去设计。
- **`test-driven-development` 里的测试金字塔（约 80/15/5）和碧昂丝规则。** *「如果你喜欢它，就该给它写个测试。」* 基础设施的改动抓不到 bug；测试才能。
- **测试里 DAMP 胜过 DRY。** Google 的测试哲学明确表示，测试代码应该读起来像一份规格，即便为此付出一些重复的代价。过度抽象的测试是已知的反模式。
- **约 100 行的 PR 粒度，配 Critical / Nit / Optional / FYI 严重性标签**，在 `code-review-and-quality` 里。直接来自 Google 的代码评审规范。大 PR 不会被评审；它们会被橡皮图章放行。
- **`code-simplification` 里的切斯特顿栅栏。** 在你理解某个东西为什么被放在那里之前，不要移除它。
- **`git-workflow-and-versioning` 里的主干开发和原子提交。**
- **`ci-cd-and-automation` 里的左移和功能开关。** 尽早抓问题，把部署和发布解耦。
- **`deprecation-and-migration` 里的代码即负债。** 你保留的每一行都是你必须永远维护的一行，所以偏爱更小的表层。

这些想法没有一个是新的。**重点是它们没有一个默认在智能体里。** 一个前沿模型在训练数据里读过「海勒姆定律」这个词组，但它在凌晨三点设计你的 API 时不会应用海勒姆定律。技能就是你确保它会应用的方式。

## 实际该怎么用

三种模式，投入大致递增。

**模式一：通过 marketplace 安装。** 如果你在用 Claude Code：

```text
/plugin marketplace add addyosmani/agent-skills
/plugin install agent-skills@addy-agent-skills
```

你会得到那些斜杠命令（`/spec`、`/plan`、`/build`、`/test`、`/review`、`/ship`、`/code-simplify`），智能体会根据上下文自动激活相关技能。这是我建议大多数人起步的路径。

**模式二：把 markdown 丢进你选的工具。** 这些技能就是带 frontmatter 的普通 markdown。Cursor 用户把它们放在 `.cursor/rules/`。Gemini CLI 有自己的安装路径。Codex、Aider、Windsurf、OpenCode，任何接受系统提示词的工具都能读它们。工具的重要性低于底下的工作流。

**模式三：把它们当规格来读。** 即便你什么都不安装，这些技能也是*一份关于「用 AI 智能体做工程，什么是好」的有文档的描述*。读 `code-review-and-quality.md`，把五轴框架用到你团队的评审流程上。读 `test-driven-development.md`，用它来决定下一次跟初级工程师的「我们到底要不要先写测试」的争论。读元技能，把五条不可协商项偷进你自己的 AGENTS.md。

我会实际从这里开始的是第三种模式。挑四五个最接近你当前痛点的技能。决定你想强制执行哪些工作流。然后再安装运行时，或者自己写一个，去做强制执行。

## 即使你从不安装，也该偷走什么

项目里有一些模式，不管你用不用 AI 编程智能体，我都会偷走。

**把反合理化当作团队实践。** 写下你团队对自己说的谎。*「发布之后我们会修测试。」「这个改动太小，不需要设计文档。」「没事，我们有监控。」* 给每一个配上反驳。放进你的 AGENTS.md 或工程 wiki。它会帮你省下争论，也会抓到下一个疲惫的周五下午的捷径。

**在你内部写的任何东西上，流程胜过散文。** 如果你发现自己在写一篇 2000 字、题为「我们如何对待 X」的文档，那你写的是参考资料。把它转换成一个带检查点的工作流。文档会缩到 400 字，而人们真的会去跑它。这同样适用于入职指南和操作手册，就像适用于智能体技能一样。

**把验证当作硬性的退出标准。** 让「产出证据」成为每个任务的退出步骤。对智能体，对工程师，对你自己。证据就是任何能证明工作完成的东西：一次绿的测试运行、一张截图、一份日志、一次评审批准。没有它，任务就没完成。*「看起来对」* 永远不算闭环。

**对任何规则手册都用渐进式披露。** 不要写一本 50 页的手册。写一个小路由器，指向适合当下情况的那一小章。这对 AGENTS.md 成立，对操作手册成立，对事故预案成立，对任何人在时间压力下要读的东西都成立。

**五条不可协商项，取自元技能，我明天就会放进任何 AGENTS.md：**

1.  动手之前先暴露假设。被默默持有的错误假设是最常见的失败模式。
2.  需求冲突时停下来问。不要猜。
3.  该反驳时就反驳。智能体（或工程师）不是一台只会说好的机器。
4.  偏爱无聊、显而易见的方案。小聪明很贵。
5.  只碰要求你碰的东西。

这就是用五行写成的、值得拥有的工程文化，而你不需要安装任何东西就能采纳它。

## 它在 harness 里的位置

放到更大的图景里看，技能是[智能体 harness 工程](https://addyosmani.com/blog/agent-harness-engineering/)的一层。harness 是模型加上你在它周围构建的一切；技能是那些被渐进式披露进系统提示词的可复用工作流块。它们和 `AGENTS.md`（滚动规则手册）、hooks（确定性执行层）、工具（智能体能采取的动作）以及会话日志（持久记忆）并列。每一层有特定的职责。技能做的是资深工程师流程的职责。

技能对[长时间运行的智能体](https://addyosmani.com/blog/long-running-agents/)比对聊天式智能体更重要，因为长时间运行会放大每一个捷径。一个在 10 分钟会话里跳过测试的智能体产生一个 bug。一个在 30 小时会话里跳过测试的智能体，会在运行结束时产生一个调试考古项目，那时候没人记得最初的意图是什么。**运行越长，资深工程师的脚手架就越必须被强制执行，而不是建议。**

技能格式的可移植性也很重要。同一个 SKILL.md 文件能在 Claude Code、Cursor（配合 rules）、Gemini CLI、Codex，以及任何接受系统提示词内容的其他 harness 里工作。把工作流写一次，运行时来强制执行。这就是带 frontmatter 的 markdown 格式买到的、而定制提示工程买不到的东西。

## 结语

我最希望人们从这个项目里拿走的，比技能本身更重要的，是那个框架。

AI 编程智能体是能力极强的初级工程师，但对那些不会出现在 diff 里的工作部分毫无直觉。资深工程的工作（暴露假设、控制改动规模、写规格、留下证据、拒绝合并不能评审的东西）正是智能体会跳过的东西，除非你让它无法跳过。这份工作越来越是：把这种纪律编码成智能体无法自我说服绕开的东西。

技能是这种编码的一种形状。反合理化表。渐进式披露。流程胜过散文。验证作为承重的退出标准。那些已经有效的 Google 实践，被做成可移植的。

你可以安装[我的版本](https://github.com/addyosmani/agent-skills)。你可以自己写。**不管哪种，这个教训都成立：工作中属于资深工程师的那些部分不再可选，即便工程师是个模型。**
