# 循环工程

> 原文：[Loop Engineering](https://addyosmani.com/blog/loop-engineering/)
>
> 发布日期：2026-06-07

---

**循环工程，就是把自己从「给智能体写提示词的人」这个角色上换掉。你转而设计一个替你写提示词的系统。** 这里的循环可以理解为一个递归目标：你定义一个目的，AI 不断迭代直到完成。我相信这可能是我们与编程智能体协作方式的未来。不过，它还很早期，我持怀疑态度，而且你绝对*必须*对 token 成本[小心](https://x.com/weswinder/status/2063700289710964906)（如果你 token 富裕或贫穷，使用模式可能天差地别），所以我想把它拆开讲讲，它是什么、意味着什么。

---

Peter Steinberger 最近[说](https://x.com/steipete/status/2063697162748260627)：「你不该再给编程智能体写提示词了。你应该设计循环，让循环去给你的智能体写提示词。」类似地，Anthropic 的 Claude Code 负责人 Boris Cherny [说](https://x.com/rohanpaul_ai/status/2063289804708835412)：「我不再给 Claude 写提示词了。我有一堆循环在运行，它们给 Claude 写提示词并弄清该做什么。我的工作是写循环。」

好吧，那这些到底是什么意思？

差不多两年来，你从编程智能体那里拿到东西的方式，是写好一个提示词、给出足够的上下文。你打一段东西，读返回的结果，再打下一段。智能体是件工具，而全程是你在握着它，一轮接一轮。那部分多多少少结束了，至少有些人认为它将要结束。

现在你构建一个小系统，由它去找工作、派活、检查、记录完成情况，然后决定下一件事，你让这个系统去戳智能体，而不是你自己。我之前写过这件事的近亲，[智能体 harness 工程](https://addyosmani.com/blog/agent-harness-engineering/)，也就是打造单个智能体运行所处的环境，以及[工厂模式](https://addyosmani.com/blog/factory-model/)——构建软件的那个系统。循环工程坐落在 harness 之上的一层。是那个 harness，但它跑在定时器上，会生出小帮手，而且自己喂自己。

让我意外的是，这已经不太算一件工具层面的事了。一年前，如果你想要一个循环，你得写一堆 bash，然后永远维护那堆 bash，它是你的，也只属于你。现在这些零件直接随产品发布。Steinberger 的清单几乎能一一对应到 Codex 应用上，然后也几乎同样对应到 Claude Code 上。而一旦你注意到形状是一样的，你就不再争论用哪个工具，你只管设计一个不管你碰巧坐在哪个工具里都仍然有效的循环。

## 五个零件，然后是一些备注

一个[循环](https://x.com/reach_vb/status/2063713960495558940)需要五样东西，再加一个记东西的地方。我先列出来，再一一对应。

1.  **自动化**，按计划触发，自己完成发现和分诊。
2.  **Worktree**，让两个并行工作的智能体不会互相踩到。
3.  **技能**，把项目知识写下来，否则智能体只能靠猜。
4.  **插件和连接器**，把智能体接进你已经在用的工具。
5.  **子智能体**，让其中一个出主意，另一个来检查。

然后是第六样，记忆。一个 markdown 文件，或者一块 Linear 看板，任何活在单次对话之外、记录着什么已完成、什么下一步的东西。听起来蠢到不值得在意。但它是每一个长时间运行的智能体都依赖的同一个诀窍，我在[长时间运行的智能体](https://addyosmani.com/blog/long-running-agents/)里深入讲过：模型在两次运行之间会忘掉一切，所以记忆必须在磁盘上，而不能在上下文里。智能体会忘，仓库不会。

两个产品现在都有这五样。

| 原语 | 在循环中的职责 | Codex 应用 | Claude Code |
|----|----|----|----|
| **自动化** | 按计划做发现 + 分诊 | [Automations 标签页](https://developers.openai.com/codex/app/automations)：选项目、提示词、节奏、环境；结果落进 Triage 收件箱；`/goal` 用于跑到完成 | 计划任务和 cron、`/loop`、`/goal`、hooks、GitHub Actions |
| **Worktree** | 隔离并行的功能 | 每个线程内置一个 worktree | `git worktree`、`--worktree`、子智能体上的 `isolation: worktree` |
| **技能** | 把项目知识写成代码 | [Agent Skills](https://developers.openai.com/codex/skills)（`SKILL.md`），用 `$name` 或隐式调用 | [Agent Skills](https://addyosmani.com/blog/agent-skills/)（`SKILL.md`） |
| **插件 / 连接器** | 连接你的工具 | 连接器（MCP）加用于分发的插件 | MCP 服务器加插件 |
| **子智能体** | 出主意并验证 | [Subagents](https://developers.openai.com/codex/subagents)，在 `.codex/agents/` 里以 TOML 定义 | `.claude/agents/` 里的任务子智能体、智能体团队 |
| **状态** | 追踪完成了什么 | Markdown 或通过连接器接 Linear | Markdown（`AGENTS.md`、进度文件）或通过 MCP 接 Linear |

名字这里那里略有不同，但能力是同一回事。让我逐个说，因为老实说，细节正是循环要么站得住、要么悄悄到处漏水的地方。

## 自动化，这是心跳

自动化是让循环成为真正的循环、而不只是你做过一次的那一次运行的东西。在 Codex 应用里，你在 Automations 标签页里建一个，选定项目、它将运行的提示词、频率，以及它跑在你的本地检出还是后台 worktree 上。找到东西的运行会进入 Triage 收件箱，什么也没找到的运行就自己归档，这点很好。OpenAI 内部用它们处理无聊的事，比如每日 issue 分诊、总结 CI 失败、写提交简报、搜捕某人上周引入的 bug。而且一个自动化可以调用技能，这样你把重复的事保持可维护，你触发 `$skill-name`，而不是把一大堵指令墙粘进一个永远不会有人更新的计划里。

Claude Code 通过调度和 hooks 到达同一个地方。你可以用 `/loop` 按间隔运行一个提示词或命令，你可以安排一个 cron 任务，你可以用 hooks 在智能体生命周期的某些时点触发 shell 命令，或者如果你希望合上笔记本后它继续跑，就把整件事推到 GitHub Actions。完全同一个思路：你定义一个自主任务，给它一个节奏，结果会送到你这里，于是你不是那个到处检查的人。

还有第二个会话内的原语值得了解，它离这篇文章的主题更近。`/loop` 按节奏重跑。`/goal` 会一直跑到你写的条件真正成立，而且每一轮之后会有一个独立的小模型检查你是否完成，所以写代码的智能体不是给它打分的那一个。你给它类似「`test/auth` 里所有测试通过且 lint 干净」这样的条件，然后走开。Codex 有同样的东西，也叫 `/goal`，它跨多轮持续工作，直到一个可验证的停止条件成立，支持暂停、恢复和清除。同一个原语，两个工具，这有点像是整篇文章的模式。

所以这部分是让工作浮现出来的那部分。循环的其余部分则对之采取行动。

## Worktree，让并行不变成混乱

你一运行不止一个智能体，文件就开始相撞，那就会变成故障。两个智能体写同一个文件，和两个工程师提交到同样的行、事先又没沟通过，是完全一样的头疼事。git worktree 能解决它：它是一个独立的工作目录、在自己的分支上，共享同一份仓库历史，所以一个智能体的编辑字面上碰不到另一个的检出。

Codex 把 worktree 支持直接做进去了，于是多个线程同时打同一个仓库也不会互相撞上。Claude Code 给你同样的隔离：`git worktree`、一个 `--worktree` 参数用来在它自己的检出里开会话，以及一个 `isolation: worktree` 设置，你把它挂在子智能体上，于是每个小帮手都拿到一个全新的检出、用完自己清理。我在[编排税](https://addyosmani.com/blog/orchestration-tax/)里写过这件事人的一面：worktree 拿走了机械层面的碰撞，但**你**仍然是天花板，你的评审带宽决定你实际能跑多少个，而不是工具。

## 技能，让你不必每次重新解释你的项目

技能是你不再像金鱼一样、每次会话都把同一份项目上下文重新解释一遍的方式。两个工具用同样的格式：一个文件夹，里面有个 `SKILL.md`，装着指令和元数据，然后是可选脚本、参考资料、素材。当用 `$` 或 `/skills` 调用时，Codex 会运行技能，或者当你的任务匹配技能描述时自动运行，这正是为什么一个紧凑、无聊的描述胜过聪明的描述。Claude Code 也是同样的做法，我把这个模式写在了[智能体技能](https://addyosmani.com/blog/agent-skills/)里。

技能也是让意图不再一次次向你收费的地方。我在[意图债](https://addyosmani.com/blog/intent-debt/)里论证过，智能体每次会话都从冷启动开始，它会在你意图里的任何空洞处填上一个自信的猜测。技能就是把那份意图写在外部：约定、构建步骤、「我们不这么做，是因为那一次事故」，一次写好，放在智能体每次运行都会读到的地方。没有技能，循环每个周期都要从零重新推导你的整个项目；有了技能，它多少会复利。

有一点要理清：技能是编写格式，插件是把技能发出去的方式。当你想跨仓库共享一个技能，或者把几个打包在一起，你就把它们打包成一个插件。在 Codex 里成立，在 Claude Code 里也成立。

## 插件和连接器，循环触及你真实的工具

一个只能看见文件系统的循环，是个很小的循环。连接器建立在 MCP 之上，让智能体能读你的 issue 跟踪器、查数据库、打一个预发环境的 API、往 Slack 丢条消息。Codex 和 Claude Code 都说 MCP，所以你为其中一个写的连接器通常直接在另一个里能用。而插件把连接器和技能打包在一起，好让你的同事一次装好你的配置，而不是凭记忆把整套东西重建一遍。

这就是「一个只会说『这是修复』的智能体」和「一个自己开 PR、关联 Linear 工单、CI 变绿后自己 ping 频道的循环」之间的差别。连接器正是循环能在你真实环境里行动、而不只是告诉你「如果它能做的话它会做什么」的原因。

## 子智能体，让做的人远离查的人

循环里最有用的结构性做法，远远地是第一名的那个：把写的人和查的人分开。写代码的模型给自己的孩子打分时实在太和气了。一个带着不同指令、有时还是不同模型的第二个智能体，能抓到第一个自己说服自己接受的东西。

Codex 只在你要求时生成子智能体，同时运行它们，然后把结果折回一个答案。你在 `.codex/agents/` 里用 TOML 文件定义自己的智能体，每个带名字、描述、指令，以及可选的模型和推理强度，于是你的安全评审者可以是一个高强度运行的强模型，而你的探索者可以是个快速的只读货色。Claude Code 用 `.claude/agents/` 里的子智能体和在它们之间传递工作的智能体团队做同样的事。两边常见的分工都是：一个探索，一个实现，一个对着规格验证。

我已经论证过两次，一次是[代码智能体乐队](https://addyosmani.com/blog/code-agent-orchestra/)，另一次是在[智能体时代的代码评审](https://addyosmani.com/blog/agentic-code-review/)里。它为什么在循环内部特别重要，是因为循环在你不看的时候运行，所以一个你真正信任的验证者，是你能够走开的唯一理由。子智能体确实更烧 token，因为每一个都做自己的模型和工具工作，所以把它们花在第二意见值得付费的地方。这也基本上就是 Claude Code 的 `/goal` 在底层做的事：让一个全新的模型决定循环是否完成，而不是那个干了活的模型，也就是把「做的人与查的人分开」应用到停止条件本身。

## 一个循环长什么样

把它们拼起来，单条线索就变成了一个小小的控制面板。这是我一直在用的一种形状。

一个自动化每天早上在仓库上运行。它的提示词调用一个分诊技能，读昨天的 CI 失败、打开始 issue、最近的提交，把发现写进一个 markdown 文件或一块 Linear 看板。对于每个值得做的发现，线程开一个隔离的 worktree，派一个子智能体起草修复，再派第二个子智能体对照项目技能和现有测试评审这份草稿。

连接器让循环能开 PR 并更新工单。循环处理不了的任何东西都落进分诊收件箱给我。状态文件是整件事的脊柱，它记住什么试过了、什么通过了、什么还开着，于是明天早上那一次运行从今天停下的地方接着来。

再看看你在那里实际做了什么。你设计了一次。你没有给那些步骤中的任何一步写提示词。这就是 Steinberger 的观点被真实地实现出来，而且它在 Codex 里和在 Claude Code 里是同一个循环，因为零件就是同样的零件。

## 循环仍然不会替你做的是什么

循环改变了工作，但并没有把你从工作里删掉。而且有三个问题会随着循环变好而变得更尖锐，而不是更容易。

验证仍然在你身上。一个无人看管的循环，也是一个无人看管地犯错的循环。你把验证者子智能体和制作者分开的整个理由，就是要让循环的「它完成了」有意义，而即便如此，「完成」也是一个主张，不是证据。我一直重复[AI 时代的代码评审](https://addyosmani.com/blog/code-review-ai/)里的那句话：你的工作是交付你确认能工作的代码。

如果你允许，你的理解仍然会腐烂。循环交付你没写过的代码的速度越快，存在的东西和你实际掌握的东西之间差距就越大。那就是[理解债](https://addyosmani.com/blog/comprehension-debt/)，而一个顺滑的循环只会让它长得更快，除非你读循环做出来的东西。

而舒服的姿态就是危险的姿态。当循环自己运行时，很容易停止持有观点，它给你什么你就接受什么。我称这个为[认知投降](https://addyosmani.com/blog/cognitive-surrender/)。带着判断去做，设计循环就是解药；为了逃避思考去做，它就是加速剂。同样的动作，相反的结果。

## 构建循环。继续当工程师。

我认为这是我们的工作将如何演进的一个预览。话虽如此，如果我不是自己评审代码，或者完全依赖自动化循环去修，我的产品质量会受损。我很可能会陷进一个向下的螺旋，不断地把自己挖进更深的坑里。

话虽如此，尽管去搭你的循环，但别忘了直接给智能体写提示词也一样有效。关键在于找到正确的平衡。

循环还可能因你而得到不同的结果。两个人可以搭出完全一样的循环，得到完全相反的结果。一个人用它在自己深懂的工作上跑得更快。另一个人用它来逃避理解这份工作。循环不知道区别。你知道。

这就是为什么循环设计比提示工程更难，而不是更容易。Cherny 的观点不是工作变简单了。而是杠杆点移动了。

构建循环。但要像一个打算继续当工程师、而不只是当那个按下开始键的人那样去构建它。
